## Purpose

Facts about the **working environment** the agent sandbox provides, and the CLI gotchas that follow.
These are not product rules. Measurements were taken on 2026-10-04 (✅ measured) unless tagged
otherwise.

**Reference environment.** All ✅ measurements were taken on 2026-10-04 against `Archont561/*`
default branches and GitHub-hosted runners; probe runs used `Archont561/pixi-release` on branch
`arena/01a10687-pixi-release`. Re-measure before relying on a toolchain fact: the sandbox image can
change between sessions.

## Network

- Reachable: `api.github.com`, `registry.npmjs.org` (HTTP 200).
- **Not** reachable, both fail with `EOF`:
  - `uploads.github.com` — release asset upload (4/4 attempts).
  - `results-receiver.actions.githubusercontent.com` — so `gh run view --log` cannot work.

Consequence for any future probe: **never plan to read Actions logs or upload release assets from
here.** Have the workflow report back through an `api.github.com`-readable surface — release body,
PR comment, or check output.

## Toolchain

- Present: `node v22.22.3`, `npx 10.9.8`.
- Absent: `pixi`, `bun`, `cargo`.
- `AGENTS.md` mandates `pixi run backlog -- …`. Pixi is unavailable, so the honest equivalent is
  `npx -y backlog.md@1.53.0 …` — the exact version pinned in `package.json`.

## GitHub credentials

- `gh auth status` → authenticated as `Archont561` via a **GitHub App installation token**, not a
  PAT. Repository permissions `admin`/`maintain`/`push`/`pull`/`triage` all true.
- `gh api repos/.../actions/permissions` → `403 Resource not accessible by integration`. The token
  can still push workflow files and dispatch runs.

## CLI gotchas

- `gh release delete <tag>` and `GET /releases/tags/<tag>` do not work on **drafts**. Address a
  draft by numeric release ID, or list and filter on `tag_name`. (Why: `doc-5`.)
- `gh run list --limit 1` immediately after a push returns the *previous* run. Filter on a changed
  run id before trusting `status: completed`.
- `backlog decision` has **no `update` subcommand**, only `create` and `list`. Decision and document
  bodies are authored in the file after CLI creation.

## Update 2026-10-24 — the restore script is committed, and it is the primary path (✅ measured)

`scripts/restore.sh` is generated by `pixi-sandbox init` (pixi-sandbox 0.8.0) and is now committed,
byte-identical to the copy in `Archont561/pixi-sandbox-starter` (`sha256:7a15fed3…`). It does what
the manual recipe below spells out — resolve `<branch_prefix>/<bundle>-<platform>` from
`pixi-sandbox.toml`, fetch that branch, unpack it, run `pixi-sandbox restore`, register the user
tools — so the manual commands are now the fallback, not the recipe.

Measured in this sandbox, from a scratch clone outside the workspace:

```bash
git clone --depth 1 --single-branch -b main https://github.com/Archont561/pixi-release.git /tmp/work
cd /tmp/work && sh scripts/restore.sh        # 57 s, ends "restore complete"
export PATH="$HOME/.local/bin:$PATH"
pixi install --frozen --offline              # no-op (one warning: no repodata cache offline)
pixi run --frozen gates                      # exit 0, 112 s, crates.io unreachable
```

It restores into the repository it is run from (`--output-path "$ROOT"`), which is why the workspace
is the wrong place for it: 1694.7 MiB unpacked plus 273.8 MiB of vendored crates would be captured in
every session snapshot. Restore into a scratch clone and copy the working tree if you need your own
edits there. `PIXI_SANDBOX_USER_TOOLS=skip` keeps `HOME` and the profile untouched.

## Update 2026-10-23 — restoring the toolchain from the published pack (✅ measured)

The absence of `pixi`, `bun` and `cargo` is no longer a hard limit. This repository publishes its
own development environment to the orphan branch `sandbox/developer-linux-64`, and that branch is a
git branch, so it is reachable from here even when conda-forge, `prefix.dev` and
`static.rust-lang.org` are not.

Measured, in order:

```bash
git clone --depth 1 --single-branch -b sandbox/developer-linux-64 \
  https://github.com/Archont561/pixi-release.git /tmp/pack      # 907 MiB, ~10 s
/tmp/pack/.pixi-sandbox/tools/linux-64/pixi-sandbox \
  doctor --branch-location /tmp/pack --verify                   # 476.3 MiB, 0 failures
/tmp/pack/.pixi-sandbox/tools/linux-64/pixi-sandbox restore \
  --branch-location /tmp/pack --output-path <scratch clone> --force   # ~39 s
pixi install --frozen --offline                                 # no-op
```

Results: `pixi 0.83.0`, `pixi-sandbox 0.8.0`, `cargo 1.98.1` and `rustc` all work afterwards. Restore
installs `pixi` and `pixi-sandbox` into `~/.local/bin`; they are not on `PATH` in an already-running
shell.

**Superseded the same day.** With `cargo_vendor = true` (REL-24) the pack also carries the crates,
and restore wires a sandbox-owned `CARGO_HOME` whose `config.toml` replaces `crates-io` with
`.pixi-sandbox/vendor`. `cargo check`, `cargo clippy -D warnings` and `cargo test` then all run with
`crates.io` unreachable, and `pixi run gates` exits 0 — measured, 11 tests passing.

Two facts to keep: the pack grew to 748 MiB and a 1.3 GB clone (vendor is 272 MiB, 36% of payload),
and `turbo` 2 runs tasks in strict env mode, so `CARGO_HOME` reaches `cargo` only because
`turbo.json` lists it in `globalPassThroughEnv`. Without that entry the lint task silently falls
back to the network.

Before REL-24 the limit was: `cargo clippy`, `cargo check` and `cargo test` did not run locally,
because the dependencies were not vendored and offline resolution stopped at `no matching package
named proptest found`.

**Size caution.** An unpacked environment is ~1.8 GB. Restore into `/tmp` or another path outside
the repository; a restore inside the workspace would swamp the session snapshot.

## Update 2026-10-23 (second session) — the session branch is local until pushed (✅ measured)

The restore recipe clones the repository, so `git checkout <session-branch>` in the scratch clone
fails while that branch exists only locally, which is how every Arena session branch starts. The
sequence that works: `git clone` the default branch, `restore` into it, then copy the working tree
across with `tar` (`rsync` is not installed here).

Also measured, correcting the row above: the pack carries `pixi` and `pixi-sandbox` itself under
`.pixi-sandbox/tools/linux-64/`, so a restore needs nothing from GitHub Releases.
`release-assets.githubusercontent.com` answers `000` from this sandbox, and downloading `pixi`
from a release asset is a dead end — not a blocker, because the pack already has it.
