## Status

Draft requirements, from the design discussion of 2026-10-20. Nothing here is implemented, and nothing here is a release rule yet. The release rules that this document depends on are `decision-8` (rebuild) and `decision-9` (registry targets wait for REL-6).

## Purpose

A framework-agnostic web component, published as a separate package, that presents a pixi-release project's releases to users. It links to the source repository and shows the release artifacts. It is used in documentation sites.

## What the component is

- A consumer of pixi-release data. It is not part of the controller and does not decide anything about releases (`decision-2`).
- JavaScript only. It does not wrap a binary and ships no binaries.
- Its own repository and its own release, released by pixi-release like any other consumer (`doc-2`).

## What it needs from pixi-release

- A machine-readable **release manifest**, one per release, in JSON (the immutable manifest format of `AGENTS.md`). The manifest lists the tag, the version, the artifacts for each platform with their SHA-256 digests, and the targets that actually succeeded.
- The component reads the manifest. It does not call the GitHub API at runtime. The manifest is either fetched from a release asset or baked into the package at its own publish time.
- Install commands, when shown, come from the manifest and only for targets that published. A target that did not succeed is never shown as installable.

## Open questions

- Manifest schema: which fields are required, and what is the schema version.
- Where the manifest lives: a release asset, a commit, or the component package.
- Whether install commands are generated by pixi-release or by the component from the manifest.
- Timing: the manifest is part of the REL-6 scope or a later task. Nothing registry-specific is in v1 (`decision-9`).
